# wechatauto 渠道：持久化游标消除重启重放风暴

## 问题

每次 Octop 后端重启（部署、崩溃、用户操作），`WechatAutoChannel` 以
`cursor=0` 启动 poll 循环，把桥内存队列里**自桥启动以来的全部事件**重新
消费一遍。2026-10-08 16:50 一次后端重启把群里已回答过的 @ 消息全部
重答了一遍（"3盏灯/玻璃瓶/小船"等题目二刷），用户可见刷屏。

`_seen` LRU 去重是进程内存态，重启即清零，救不了这个场景。

## 为什么选 boot_id 键控的持久游标

关键在于区分两种重启：

- **adapter 重启、桥没动**：队列里旧事件都被消费过 → 必须续游标，
  否则重放 = 今天的事故
- **桥重启、seq 归零**：新队列只含 adapter 没见过的真事件 → 必须从 0，
  否则旧游标（如 42）会让 seq 1..N 的新事件被永久跳过

光看 seq 大小无法区分这两种情况（新桥 seq=1 既可能"小于旧游标"也可能
"该被消费"），所以需要桥提供一个进程级标识符。bridge `/health` 返回
`boot_id`（uuid4/进程），adapter 把 `{boot_id, cursor}` 持久化到
`~/.wechatauto/octop-cursor-<channel_id>.json`：启动时 boot_id 匹配才续，
否则归零。

## 放弃的替代方案

- **事件级持久去重**（持久化 `_seen`）：状态量更大、语义更绕；游标天然
  是消费进度的最小表达。
- **重启时跳到队列尾**（cursor=latest）：会丢弃停机期间的真消息；
  聊丢了比重答更糟。
- **桥侧按消费者记账**：桥需要跟踪每个消费者的水位，复杂度上移，
  而且桥被多宿主共享（Hermes/OpenClaw），协议面会变宽。

## 语义细节

- **at-least-once**：先 dispatch 整批事件再推进+持久化游标。进程若在
  dispatch 后、保存前死，重启时该批重放一次（有界重复 > 静默丢失）。
- **旧桥降级**：`/health` 无 `boot_id` → 持久化整体关闭，行为同改前。
- **state_file** 配置项可覆盖默认路径（测试用），`from_dict` 对未知
  字段宽容，旧 config_json 无需迁移。

## 验证

- 单测 5 项：匹配续游标 / boot_id 不匹配归零 / 无 boot_id 不写盘 /
  落盘格式 / 无状态文件归零
- 生产实证：toggle 重注册后日志出现 `resuming cursor=1 (boot_id match)`，
  poll loop 以 cursor=1 启动，无重放
